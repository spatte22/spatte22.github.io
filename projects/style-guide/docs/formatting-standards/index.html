Formatting Standards

This page addresses how content should display on pages, along with related "microstyle" standards.

Voice​

  • Follow the guidelines for the three modes, user guide, developer, and educator.
  • In general, use a casual yet professional voice and tone.
  • Do not use the first-person perspective.
  • Use second-person perspective (You can do this or that).
  • DO not use marketing fluff. Show value in other ways, like examples or use cases.
  • Do not use unnecessary enthusiasm, like exclamation marks or emojis.

Headings​

  • Capital case
  • Use descriptive headings that reflect system concepts, not vague labels.
  • Avoid generic titles such as “Overview” unless introducing a full section.
  • Favor "Set Up..." and "Manage..." verbiage for task-based pages.
  • Avoid lengthy headings that wrap onto a second line.
  • Favor ample styling to distinguish between headings, in particular H2's and H3's.
  • Do not use gerunds (ie: Using the Dashboard)

Lists​

  • Use numbered steps for procedural tasks.
  • Use bullet lists for conditions, attributes, or conceptual grouping.
  • Introduce unordered lists, often ending with a colon.
  • Punctuate list items consistently within a list.
    • If one item needs punctuation, then all items need it.
    • It's acceptable for different lists on the same page to have inconsistent punctuation, as long as the punctuation within the list is consistent.
  • A nested list must have at least two items.

Images​

In general, use images sparingly. Be wise and add an image where the user needs extra context. Do not add an image for each step of a task.

  • Users typically have multiple monitors or multiple windows open at the same time. Therefore, they're usually reading documentation and toggling back and forth with their other interface. This usually means that screenshot usage can be reduced.
  • Too many images can ruin the flow of information and actually be cumbersome for the reader.
  • Too many images can be a time sink to manage.
  • In general, do not capture an entire screen as a screenshot. Instead, focus on where the user needs to perform an action and include enough context for the image to be useful.

Hyphenation​

The trend is to avoid hyphenation, however, use it where it makes sense. Generally follow the Microsoft guidance.

Hyphens are acceptable, particularly where prefixes may be confusing.

For example:

If necessary, resign the document.

versus

If necessary, re-sign the document.

Contractions​

Be purposeful in using contractions. Generally avoid them, but they are acceptable, depending on the context. For example, in a less formal guide for basic users, it's okay. For administrative information, it can be acceptable unless referring to something critical, like a warning.

For example:

You may want to {do something} if you don't want {something}. However, do not disable {something}.

Code Blocks​

  • Keep examples focused and minimal.
  • Follow examples with explanation when necessary (or include comments).
  • Be sure to use language-specific styling.
  • Favor putting code blocks in expandable drop-downs.

Emphasis​

  • Use bold sparingly for UI labels or critical terms.
  • Be purposeful in typographic decoration; use it to denote UI or clickable elements and occasionally italicized emphasis.
