Core Writing Principles

This page defines general principles that apply to most all content I write.

Concept Before Mechanism​

Documentation must define what a system component is before explaining how to configure or use it. A basic guideline is to introduce a concept by explaining the what/why/where/how/who.

Readers should understand concepts, purpose, and use cases before interacting with implementation steps.

Preferred structure:

  1. Definition or contextual framing
  2. System relationship or architectural role
  3. Implementation overview

Example pattern:

An OAuth application defines how your integration authenticates with the platform. After creating the application, you must configure redirect URIs and assign scopes.

This approach prevents task-based documentation from becoming instruction without understanding.

Content Structure​

Adhere to the topic-based authoring approach as a default:

  • Concept topics
  • Task topics
  • Referential topics

This is typically more pertinent to user guides, not developer docs.

Logical Progression and Layered Structure​

Documentation should follow a predictable progression:

  1. Overview
  2. Prerequisites
  3. Configuration or implementation
  4. Example
  5. Edge cases or advanced considerations
  6. Outcome or validation

Not all sections are required in every document, but the sequence should remain intuitive.

Readers should not encounter:

  • Deep configuration before context
  • Advanced examples before baseline explanation
  • References to undefined terminology

Layered structure reduces cognitive load and supports multiple skill levels.

Structured Density Over Narrative Density​

Documentation should prioritize structural clarity over paragraph length. Nobody wants to read a wall of text.

Preferred formatting includes:

  • Subheadings for scannability
  • Lists for multi-condition explanations
  • Segmented procedural steps
  • Clear separation between conceptual explanation and configuration instructions

Dense narrative paragraphs are avoided when structural segmentation improves readability.

Architecture-Aware Writing​

Documentation should reflect system relationships, not isolated UI actions.

Where applicable, content must clarify:

  • What depends on what
  • What triggers what
  • What changes system state
  • What fails if misconfigured

Configuration steps are incomplete without explaining system impact.

Readers should be able to infer:

  • How components interact
  • Where failures may originate
  • What layer of the system they are modifying

This principle ensures documentation scales beyond simple UI walkthroughs.

Action and Consequence Pairing​

Step-by-step instructions should include context about outcomes, constraints, or validation behavior.

Enterprise systems have operational impact. Documentation must reflect that.

Instead of:

Enter the redirect URI.

Prefer:

Enter a redirect URI that exactly matches the value configured in your client application. If the values do not match, the authorization request is rejected.

When appropriate, documentation should clarify:

  • Failure conditions
  • Validation requirements
  • Permission implications
  • Security implications

This reinforces accuracy and reduces support burden.

Terminology Discipline​

Key terms must be:

  • Introduced before heavy reuse
  • Used consistently
  • Not interchanged casually

Where necessary, documentation should define:

  • System-specific terms
  • Role names
  • Object types
  • System entities

Terminology inconsistency creates architectural confusion. Precision builds authority.

Declarative Sentence Construction​

Sentences should be:

  • Direct
  • Clear
  • Moderate in length
  • Active when possible

Avoid:

  • Overuse of passive voice
  • Unnecessary qualifiers
  • Emotional emphasis (exclamation marks and emojis)
  • Informal filler

Even when tone varies by audience, sentence construction remains controlled.

Contrast as an Explanatory Tool​

Where appropriate, contrast clarifies understanding.

Examples:

  • OAuth application vs service account
  • Manual configuration vs automated provisioning
  • Individual API request vs batch processing
  • Timeline vs single animation instance

Contrast should highlight system behavior differences, not stylistic variation.

Example as Reinforcement, Not Decoration​

Code samples and configuration examples must:

  • Represent realistic usage
  • Demonstrate core concepts
  • Avoid trivial filler
  • Reinforce architectural understanding

Examples exist to clarify behavior, not to fill space.

Audience Respect​

Documentation should not assume incompetence, nor should it assume expert-level context without framing.

The writing should:

  • Avoid condescension
  • Avoid oversimplification
  • Avoid unnecessary complexity

Readers need to feel guided, not managed.

tip

For administrator or developer type audiences, target a 9th-grade reading level (or below).

For basic users or non-technical audiences, target a 7th-grade reading level (or below).
